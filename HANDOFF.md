## v2.0: Standard v1 (READ THIS FIRST; it supersedes the v1.3 "Autopilot / Manual" and "match" sections below)
One rule for everyone: **trade size = the account's OWN balance x a percent (default 20%)**, capped at $500 of margin per trade, never more than the free balance.
Position = margin x the signal's leverage / price, rounded DOWN to Bybit's step. Leverage, stop loss, take profit and trailing come from the signal exactly; nothing overrides them.
- Floor rule: if rounding leaves less than Bybit's minimum order, the minimum is used instead only when it needs <= 1.5x the chosen margin AND <= 35% of the balance (and fits the free balance). Otherwise the trade is skipped with a plain-language reason (code MINQ). Constants live in `STD` at the top of multiuser.js.
- Users choose their own size (percent 1-30, anything over 20 needs `confirmHigh:true`, or a fixed USD amount) on /join "Your trade size". No Autopilot/Manual switch any more: `effective(u)` always uses the user's own size columns; `/api/me/mode` is a harmless no-op kept for old open pages.
- Plan (`master_plan`) now holds: default sizing for NEW sign-ups (sizePct 20), `maxTradeUsd` 500, rails `maxOpenTrades` 3 (admin max 5), `dailyLossPct` 10 (of the balance the day started with, from equity_snap or balance minus today's PnL), `drawdownStopPct` 30, optional `dailyLossLimitUsd` / `dailyProfitTargetUsd`, coins, direction. `maxLeverage` is ignored (kept only so old stored plans load). `sizeMode:'match'` is retired: parseControls rejects it; stored plans containing it are read as 20%.
- Optional admin ceilings per user (max_trade_usd, max_lev_ceiling) and the env cap MAX_USER_LEVERAGE still exist but are OFF by default. Those are the only things that can change a signal's leverage; Bybit's own per-coin limit can also clamp it.
- **Migration (runs once on first start, meta flag `std_v1_migrated`)**: users on "match" (their own, or because the plan was match) become percent = 10 x their multiplier, clamped 1-30, and get a one-time notice shown on their page (users.notice). Users already on fixed/percent keep exactly their amount. The plan moves to the Standard, keeping any rails the admin had set. A row the migration missed still trades safely (sizeForUser/effective read `match` as 10% x multiplier).
- Sign-up is 4 steps (account, make key, paste key, trade size + risk tick box). Live accounts need >= $50 (env MIN_LIVE_BALANCE, 0 turns it off); demo has no minimum. The starting size and risk acknowledgement are stored (users.size_*, risk_ack_at).
- **Signal ledger**: bots POST `open|relay|close|status` events to `/api/bot-event` (device key via requireDevice). Table `signals` is keyed by the bot's `k` (idempotent; out-of-order safe), `bot_status` keeps the latest status per bot. `order_log.signal_key` ('ym-<rid>') links each user's copy to the signal, `risk_usd` stores the estimated loss if the stop is hit.
- **Alarm**: a signal with relay=SENT that has no order at the relay after SIGNAL_ALARM_SECONDS (default 60) sends ONE Telegram alert to the admin chat ("the bot says it sent this trade but nothing arrived"). An order or manager exec-report for its rid counts as arrived; late-reported signals are checked against orders that already came in.
- Admin Activity tab starts with "Signals" (GET /api/admin/signal-ledger). Users see "Signals for you" on the Trades tab (GET /api/me/activity): copied (with the loss if the stop is hit) or not copied and why.
- **Master follows the plan (OFF by default)**: env `MASTER_FOLLOWS_PLAN=true` makes server.js processOrder replace the quantity of the master's OPEN orders with the same sizing rule (master balance x plan percent, $500 cap, at the leverage already set for the pair). Closes, a pair already held, paper mode, or anything that can't be sized keep the manager's own quantity. No firmware change is needed either way. Leave it off while the bots' relay margin ($100) is what you want for the master.
- Device key: unchanged and still `warn` by default. To enforce: put the same value in Render `DEVICE_API_KEY` and in the manager's `deviceKey` (and bots' `ORACLE_WEB_DEVICE_KEY`), watch the admin Security check, then set `DEVICE_KEY_MODE=enforce`.
- server.js changes in v2.0: `requireDashboardOrDevice` on /api/balance and /api/positions (the manager can read them with X-Device-Key), `/api/bot-event`, master sizing hook in processOrder.
- Tests: tests/integration.test.js 88 checks (needs local Postgres on port 54329 and, for the page checks, JSDOM_DIR=<folder with jsdom>), tests/server.test.js 19 (set TEST_DATABASE_URL for the last 8), dashboard.ui / dashboard.account.ui unchanged and passing. NOT tested: real ESP32 hardware, real Bybit, a real Render/Neon deploy.
- Rollback: redeploy the previous commit. The new columns/tables are additive, so the old code still runs. One catch: the migration already rewrote users' size columns and the stored plan; the old code would read those as fixed/percent users (fine) and a percent plan. Back up the database first (Neon: create a branch) if you want a clean path back.


## What this is
Express relay on free Render, fed by ESP32 "oracle" bots. Optional multi-user mode copies each signal to invited
users' Bybit accounts, scaled by equity, and logs USD PnL permanently in Neon Postgres.
Owner is a beginner in Nigeria (Africa/Lagos). Explain things step by step in plain language.

## v1.3: Master Plan, Autopilot / Manual
Admin sets ONE master plan (admin.html "Master plan"; GET/POST /api/admin/plan; stored in meta key `master_plan`). Every account is on AUTOPILOT by default and follows it.
Plan fields: sizing (match x multiplier | fixed USD margin | % of balance), coins, direction, max open trades, max leverage, daily loss limit, daily profit target, drawdown stop %, allowManual.
- `effective(u)` merges plan + user row. Autopilot = everything from the plan. Manual = user may override ONLY size_mode/size_mult/size_usd/size_pct/daily_loss_limit_usd
  (MANUAL_KEYS); coins, direction, max open, leverage, profit target and drawdown always come from the plan. allowManual:false forces everyone to autopilot (saved values kept).
- Going manual: POST /api/me/mode {mode:'manual', password, ack:true}. Wrong password counts as a failed login (lockout). Starts from the plan's values (100% match).
  UI: warning sheet with hazard stripe, tick box, password, safety cover + press-and-hold button. Back to autopilot needs no password.
- Gauge: planMatch() = 70 x sizing similarity + 30 x loss-limit similarity (same formula copied in join.html).
- "Restore to plan values" = /api/me/reset-defaults (manual only; never touches key/password/2FA/Telegram/pause). Admin can "Force autopilot" per user (POST /api/admin/users/:id {controlMode:'auto'}).
- Per-user admin ceilings still exist: max_trade_usd, max_lev_ceiling (lowering pulls the user's amount down; lowest leverage cap wins).
- Pause all users (meta users_paused_all; opens only), Close all users' trades (type CLOSE), per-user pause / close-all / pause-and-close.
- Stop rules: drawdown uses equity_peak, reset on resume, on a plan drawdown change, and on restore.
- Order codes: FILT, MAXT quiet (logged ok); MINQ/BAL/HALT give the user a plain message.
- Schema changes are ALTER ... IF NOT EXISTS on every start (control_mode, manual_ack_at plus the v1.2 columns). No manual migration.

## v1.4: admin console, plan history, dry run
- **Console** (admin.html): tabs Overview | Users | Plan | Activity | Payments (placeholder), URL hash remembers the tab. Always-visible top bar: Dry run, Pause all, Close all, invite, sign out, and chips (LIVE / DRY RUN / PAUSED, plan version, autopilot vs manual counts).
  Overview = tiles + "Needs attention" list from GET /api/admin/overview (key errors, paused, 3+ failed orders/24h, repeated MINQ/BAL skips, manual users under 60% plan match, signed up >1 day without a key) with one-click fixes. Users tab has search + filters.
- **Plan history**: table `plan_versions` (plan JSON, changed_by, summary, restored_from). Every plan save = new version with a readable diff summary; the live version id is stamped on every order_log row (`plan_version`).
  POST /api/admin/plan/preview (diff + how many accounts it touches, saves nothing), GET /api/admin/plan/history, POST /api/admin/plan/restore {id} (restores as a NEW version; history is never rewritten). UI: "Review changes" panel before "Apply".
- **Dry run**: global (meta `dry_run_all`, POST /api/admin/dry-run {enabled}) or per user (users.dry_run via POST /api/admin/users/:id {dryRun}). Everything runs for real up to and including sizing, then logs code `DRY` ("would buy 0.03 BTC at 5x") instead of sending.
  Dry accounts get NO order, leverage or stop-loss calls. Closes (reduce-only) and the user's own close-all always go through, like pause. Retransmits log once (link `dry-...`). Users see a "test mode" box on their page. DRY is a quiet code (no Telegram ping).
  A dry run cannot catch Bybit rejecting an order: it tests the plan and sizing, not the exchange.
- GET /api/admin/orders now takes user, code, failed=1, dry=1; GET /api/admin/orders/summary?hours= counts result codes per user.
- Schema additions (idempotent): users.dry_run, order_log.plan_version, plan_versions.

## v1.7: demo and live users side by side
- Each user has `users.key_env` ('live' or 'demo'). Chosen at sign-up (Live account / Demo practice) and changeable in Settings > Bybit key.
- A user's Bybit client is built from THEIR environment (envOpts in multiuser.js). BYBIT_DEMO / BYBIT_TESTNET / BYBIT_BASE_URL now describe the MASTER account only and never reach a user's client.
- Switching demo<->live: results of the environment being left are moved to pnl_ledger_old / funding_ledger_old (kept, never mixed in), the sync clock restarts, and the user is PAUSED until they resume.
- Admin totals (equity, PnL today/week/total) count LIVE users only; demo users carry a DEMO tag and are counted separately (tiles.demoUsers). Telegram alerts for demo users start with [DEMO].
- Users that existed before v1.7 take the relay-wide environment they were trading in (demo if BYBIT_DEMO is on or BYBIT_BASE_URL contains api-demo, otherwise live), once.
- Known limits: demo balances are often huge, so size scaling is capped by MULTIUSER_MAX_RATIO (default 10x the master). Demo users only receive signals while the master is live; copying while the master is in paper mode is not built.
- tests/integration.test.js: 83 checks (set RELAY_DIR; JSDOM_DIR for the page checks). tests/server.test.js: 12 checks (set RELAY_DIR).

## v1.8: master key from the dashboard + landing page
- Dashboard > Settings > Trading account: change the MASTER Bybit key/secret (and Live/Demo) without touching Render.
